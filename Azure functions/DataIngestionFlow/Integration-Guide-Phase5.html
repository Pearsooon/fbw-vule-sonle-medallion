Phase 5: Tái cấu trúc Storage 3-container & Pipeline merge vào Bronze Lakehouse

Cập nhật theo sơ đồ kiến trúc mới: Storage Account giờ có 3 container (pre-raw, staging, archive) thay vì 1 container relay duy nhất. Data Lake Adapter chuyển vai trò từ "ghi vào SQL SIT/STT" sang "convert .xlsx → .csv". Việc merge dữ liệu vào Bronze Lakehouse (.parquet) được tách ra thành một Fabric Data Pipeline riêng, chạy tự động theo trigger — không còn đi qua SQL SIT/STT Warehouse nữa.

Task 1

🗄️ Task 1 — Tái cấu trúc Storage Account thành 3 container

Dùng lại Storage Account đã có từ Phase 2 (nrn-academy-st-dev-{name}, có thể đang hiển thị với tên thực tế khác như stsonlesea tuỳ quy ước nội bộ) — không tạo Storage Account mới, chỉ thêm container và đổi vai trò container cũ.

1  Tạo/đổi tên 3 container

  1. Portal → Storage Account → menu trái Containers.
  2. Container ingest-relay (đã có từ Phase 2): đổi vai trò thành pre-raw.
    • Lưu ý: Azure Storage không hỗ trợ rename container trực tiếp. Cách đơn giản nhất: tạo container mới tên pre-raw, sau đó cập nhật lại đường dẫn trong Logic App (Task 2) để trỏ vào container mới này. Có thể giữ ingest-relay tồn tại song song trong giai đoạn chuyển đổi rồi xoá sau khi xác nhận luồng mới hoạt động ổn định, hoặc dùng Azure Storage Explorer/AzCopy để copy toàn bộ blob hiện có từ ingest-relay sang pre-raw nếu cần giữ lại dữ liệu cũ.
  3. Tạo container mới staging — nơi Data Lake Adapter ghi file .csv đã convert.
  4. Tạo container mới archive — nơi lưu lại file .xlsx gốc sau khi đã convert xong.
  5. Access level cho cả 3 container: Private (giữ nguyên nguyên tắc từ Phase 2 — không public, truy cập qua managed identity).

Mở rộng tiếp nrn-academy-logic-ingest-dev-{name} (đã có từ Phase 1–2) — chỉ cần đổi container đích trong action "Create blob", không đổi trigger hay action khác.

Task 3

🧩 Task 3 — Data Lake Adapter: Convert + Archive (bỏ ghi Warehouse)

Đây là thay đổi lớn nhất Phase 5: code DataLakeAdapter (đã có từ Phase 2 và mở rộng ở Phase 4) bỏ hẳn phần ghi vào SQL SIT/STT Warehouse. Vai trò mới của Adapter chỉ còn: detect loại file (giữ nguyên logic quarantine từ Phase 4), convert .xlsx → .csv, ghi vào staging, và archive file gốc.

1  Cập nhật quyền managed identity

Trước khi sửa code, cập nhật role assignment cho Function App trên Storage Account (Phase 2 chỉ cấp quyền đọc):

  1. Portal → Storage Account → Access Control (IAM) → + Add role assignment.
  2. Role: Storage Blob Data Contributor (bao gồm cả đọc lẫn ghi — thay thế Storage Blob Data Reader đã gán ở Phase 2, vì giờ Adapter cần ghi vào staging và archive).
  3. Assign to: Managed identity của nrn-academy-func-dev-{name}.

2  Code Adapter — Phase 5: convert + ghi staging + archive

// DataLakeAdapter.cs — Phase 5: convert .xlsx → .csv, KHÔNG còn ghi Warehouse
[Function("DataLakeAdapter")]
public async Task<HttpResponseData> Run(
    [HttpTrigger(AuthorizationLevel.Function, "post")] HttpRequestData req)
{
    var body = await req.ReadAsStringAsync();
    var eventData = JsonSerializer.Deserialize<IngestEventPayload>(body);
    var blobUrl = eventData?.Data?.BlobUrl;
    var fileName = eventData?.Data?.OriginalFileName ?? "";
    var extension = Path.GetExtension(fileName).ToLowerInvariant();

    var sourceBlobClient = new BlobClient(new Uri(blobUrl), new DefaultAzureCredential());
    using var sourceStream = new MemoryStream();
    await sourceBlobClient.DownloadToAsync(sourceStream);
    sourceStream.Position = 0;

    var supportedExtensions = new[] { ".csv", ".xlsx", ".xls" };
    if (!supportedExtensions.Contains(extension))
    {
        _logger.LogWarning("Unsupported file type '{Ext}' for '{FileName}' — quarantine.", extension, fileName);
        await MoveToQuarantineAsync(sourceBlobClient, fileName);
        return req.CreateResponse(HttpStatusCode.OK);
    }

    // 1. Convert .xlsx/.xls → .csv (nếu đã là .csv thì bỏ qua bước convert)
    string csvContent = extension == ".csv"
        ? await new StreamReader(sourceStream).ReadToEndAsync()
        : ConvertExcelToCsv(sourceStream);

    // 2. Ghi .csv vào container "staging"
    var csvFileName = Path.GetFileNameWithoutExtension(fileName) + ".csv";
    await WriteToStagingAsync(csvContent, csvFileName);

    // 3. Copy file .xlsx gốc sang container "archive"
    await ArchiveOriginalFileAsync(sourceBlobClient, fileName);

    // Phase 5 scope ends here.
    // Merge .csv vào Bronze Lakehouse (.parquet) do Fabric Data Pipeline đảm nhiệm (Task 4) — KHÔNG còn trong Adapter.

    _logger.LogInformation("Converted {FileName} → {CsvFileName}, written to staging, archived original.",
        fileName, csvFileName);

    return req.CreateResponse(HttpStatusCode.OK);
}

private string ConvertExcelToCsv(Stream excelStream)
{
    using var workbook = new XLWorkbook(excelStream);
    var worksheet = workbook.Worksheets.First();
    var range = worksheet.RangeUsed();

    var sb = new StringBuilder();
    foreach (var row in range.RowsUsed())
    {
        var values = row.Cells().Select(c => EscapeCsvField(c.GetString()));
        sb.AppendLine(string.Join(",", values));
    }
    return sb.ToString();
}

private static string EscapeCsvField(string field)
{
    if (field.Contains(',') || field.Contains('"') || field.Contains('\n'))
        return $"\"{field.Replace("\"", "\"\"")}\"";
    return field;
}

private async Task WriteToStagingAsync(string csvContent, string csvFileName)
{
    var stagingContainer = new BlobContainerClient(
        _storageAccountUri.Replace("pre-raw", "staging"), new DefaultAzureCredential());
    await stagingContainer.CreateIfNotExistsAsync();

    var blobClient = stagingContainer.GetBlobClient(csvFileName);
    using var stream = new MemoryStream(Encoding.UTF8.GetBytes(csvContent));
    await blobClient.UploadAsync(stream, overwrite: true);
}

private async Task ArchiveOriginalFileAsync(BlobClient sourceBlob, string fileName)
{
    var archiveContainer = new BlobContainerClient(
        sourceBlob.GetParentBlobContainerClient().Uri.ToString().Replace("pre-raw", "archive"),
        new DefaultAzureCredential());
    await archiveContainer.CreateIfNotExistsAsync();

    var destBlob = archiveContainer.GetBlobClient(fileName);
    await destBlob.StartCopyFromUriAsync(sourceBlob.Uri);
}
Đã loại bỏ khỏi code: toàn bộ phần WriteToWarehouseAsync, SqlConnection tới wh-vule-sonle-WWI-medallion, và package Microsoft.Data.SqlClient không còn cần thiết trong Function App này nữa (có thể gỡ reference nếu không dùng cho mục đích khác). Toàn bộ phần GRANT INSERT cho Service Principal trên Warehouse ở Phase 4 cũng không còn áp dụng cho luồng này.
Vì sao archive bằng copy thay vì move: mẫu code dùng StartCopyFromUriAsync (copy, giữ lại file gốc ở pre-raw) thay vì xoá file gốc sau khi copy. Nếu muốn dọn pre-raw để tránh phình dung lượng, có thể thêm bước await sourceBlob.DeleteIfExistsAsync() sau khi xác nhận copy thành công — cân nhắc đặt lifecycle policy tự xoá thay vì xoá ngay trong code, để có thời gian rollback nếu phát hiện lỗi convert.
Task 4

🚀 Task 4 — Fabric Data Pipeline: merge staging → Bronze (.parquet)

Tạo mới 1 Fabric Data Pipeline trong workspace chứa lh_vule_sonle_medallion — đọc file .csv từ container staging, ghi vào Bronze layer của Lakehouse dưới định dạng .parquet, chạy tự động theo schedule trigger.

1  Tạo Data Pipeline

  1. Vào workspace Fabric chứa lh_vule_sonle_medallion → + New item → Data Pipeline.
  2. Đặt tên: pl_staging_to_bronze_{name}.
  3. Thêm activity Copy Activity vào canvas pipeline.

1.1 — Cấu hình Source (đọc từ staging)

  1. Tab Source của Copy Activity → Connection → tạo connection mới tới Storage Account:
    • Connection type: Azure Blob Storage
    • Account name: nrn-academy-st-dev-{name} (hoặc tên thực tế)
    • Authentication: Organizational account (dùng tài khoản Office 365 của bạn — tương tự cách Logic App đã làm ở Phase 2, không cần App Registration, phù hợp với việc bạn không có quyền tạo App Registration)
  2. File path: container staging, pattern *.csv (đọc toàn bộ file CSV trong container).
  3. File format: DelimitedText (CSV), First row as header: bật (đúng theo cách Adapter đã ghi header ở Task 3).

1.2 — Cấu hình Destination (ghi vào Bronze Lakehouse)

  1. Tab Destination → Connection: chọn trực tiếp Lakehouse lh_vule_sonle_medallion (Fabric Data Pipeline có connector native tới Lakehouse trong cùng workspace, không cần connection string riêng).
  2. Root folder: Files hoặc Tables tuỳ cách bạn tổ chức Bronze layer hiện tại (theo pattern Medallion đã dùng ở Velocity Framework Exercise — Bronze thường lưu dạng Files/Parquet theo từng nguồn).
  3. Đường dẫn đích: ví dụ Bronze/sharepoint_excel/{fileName} — điều chỉnh theo cấu trúc Bronze thật của bạn.
  4. File format đích: Parquet.
  5. Copy behavior: chọn Merge files nếu muốn gộp nhiều CSV thành 1 file Parquet, hoặc Preserve hierarchy nếu muốn giữ mỗi file CSV thành 1 file Parquet riêng — tuỳ cách bạn muốn tổ chức Bronze (giữ riêng từng lần ingest dễ truy vết nguồn hơn, gộp lại tiết kiệm số file nhỏ).
Vì sao dùng "Organizational account" thay vì Service Principal: giống lý do Logic App ở Phase 2 dùng connector SharePoint qua tài khoản Office 365 cá nhân — Fabric Data Pipeline cũng hỗ trợ xác thực bằng chính tài khoản Entra ID của bạn khi tạo connection, không bắt buộc phải có App Registration. Đây là lựa chọn nhất quán với toàn bộ hướng "không dùng App Registration" đã chốt từ Phase 2.

2  Thiết lập Schedule Trigger tự động

  1. Trong pipeline editor, vào tab Home → Schedule (góc trên bên phải).
  2. Bật Scheduled run.
  3. Chọn tần suất, ví dụ mỗi 15 phút hoặc mỗi giờ tuỳ độ trễ chấp nhận được giữa lúc file vào staging và lúc dữ liệu xuất hiện ở Bronze (cân nhắc giữa độ tươi dữ liệu và chi phí Capacity Unit — chạy quá dày sẽ tốn CU dù không có file mới).
  4. Start date/time: ngay bây giờ hoặc theo lịch bạn muốn.
  5. Save pipeline.
Idempotency — tránh merge trùng file đã xử lý: vì pipeline chạy theo schedule (không phải event-based theo từng file mới), cần đảm bảo Copy Activity không merge lại file CSV đã xử lý ở lần chạy trước. Cách đơn giản nhất: sau khi Copy Activity hoàn tất, thêm 1 activity Delete (hoặc Move nếu Fabric Pipeline hỗ trợ) để dọn file CSV đã merge khỏi staging — đảm bảo mỗi file chỉ được merge đúng 1 lần dù pipeline chạy lặp lại định kỳ.

Cost

💰 Cost Phase 5

Phase 5 không tạo thêm Azure resource billable mới ngoài 2 container bổ sung (gần như miễn phí ở quy mô nhỏ). Chi phí cần theo dõi chính là Fabric Capacity Unit (CU) tiêu thụ bởi Data Pipeline chạy theo schedule.

Thành phầnCơ chế tính tiềnGhi chú Phase 5
2 container mới (staging, archive) Theo GB lưu trữ + transaction, giống pre-raw. Không đáng kể ở khối lượng test — dưới $0.10/tháng.
Fabric Data Pipeline (schedule trigger) Tiêu thụ CU của capacity hiện có mỗi lần chạy — tần suất chạy càng dày, CU tiêu thụ càng nhiều dù không có file mới để xử lý. Nếu capacity đã sẵn có (như Warehouse/Lakehouse hiện tại), không phát sinh cost mới trực tiếp, nhưng cần theo dõi nếu lịch chạy quá dày gây cạnh tranh CU với các pipeline/notebook khác đang chạy trên cùng capacity.
≈ $0 cost mới phát sinh trực tiếp
Rủi ro duy nhất cần theo dõi là CU usage nếu đặt schedule trigger quá dày (ví dụ mỗi 1–5 phút) — nên bắt đầu với tần suất thưa (15–60 phút) và điều chỉnh dần dựa trên Fabric Capacity Metrics App, thay vì đặt dày ngay từ đầu.
