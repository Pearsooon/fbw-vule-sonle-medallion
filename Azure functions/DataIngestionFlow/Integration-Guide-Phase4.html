Phase 4: Kết nối Data Lake Adapter vào Warehouse & Consumer vào Lakehouse

Phase cuối cùng — nối 2 đầu còn thiếu của toàn kiến trúc: Data Lake Adapter parse file CSV/Excel thật và ghi vào Fabric Warehouse wh-vule-sonle-WWI-medallion (đóng vai trò SQL SIT/STT), và Consumer Function query dữ liệu thật từ Lakehouse lh_vule_sonle_medallion để trả về Email/Push. 📐 Tổng quan Phase 4

Đây là phase kết nối toàn bộ kiến trúc thành 1 luồng hoàn chỉnh end-to-end. Hai việc chính:

  1. Data Lake Adapter (Flow 1): thay vì chỉ pull blob và log như Phase 2, giờ Adapter phải detect loại file, parse nội dung CSV/Excel thành dữ liệu có cấu trúc, và ghi vào Fabric Warehouse (SIT/STT) wh-vule-sonle-WWI-medallion.
  2. Consumer (Flow 2): thay vì chỉ log placeholder như Phase 3, giờ Consumer query dữ liệu thật từ Lakehouse lh_vule_sonle_medallion để đưa vào nội dung Email/Push.

Luồng dữ liệu hoàn chỉnh sau Phase 4

SharePoint → Logic App → Storage Account → Event Grid → APIM → Data Lake Adapter (parse + write Warehouse)  |  External System → APIM → Publisher → Service Bus → Consumer (query Lakehouse) → Email (ACS) + Push (Notification Hubs)

📄 Xử lý loại file: CSV/Excel hợp lệ vs file khác (PDF...)

Theo phạm vi đã chốt, Data Lake Adapter chỉ xử lý dữ liệu có cấu trúc (CSV, Excel). Các loại file khác (PDF, Word, ảnh...) không nằm trong khả năng parse hiện tại — Adapter sẽ detect loại file ngay từ đầu và rẽ nhánh: hợp lệ thì xử lý tiếp, không hợp lệ thì quarantine (chuyển vào khu vực riêng + log) thay vì cố xử lý hoặc làm crash pipeline.

Vì sao quarantine mà vẫn trả 200 OK cho file không hỗ trợ: nếu Adapter trả lỗi 4xx/5xx cho file PDF, APIM/Event Grid có thể retry nhiều lần một cách vô nghĩa (vì file đó vẫn sẽ luôn fail). 📥 Task 2 — Data Lake Adapter: Parse file thật + ghi vào Warehouse

Mở rộng code DataLakeAdapter đã có từ Phase 2 (pull blob qua Blob SDK) — thêm 3 bước: detect loại file, parse nội dung nếu hợp lệ, ghi vào Warehouse wh-vule-sonle-WWI-medallion.

1  Detect loại file + nhánh quarantine

  1. Cài thêm package SDK trong project Function App Adapter:
dotnet add package CsvHelper
dotnet add package ClosedXML

// DataLakeAdapter.cs — Phase 4: detect + route theo loại file
[Function("DataLakeAdapter")]
public async Task<HttpResponseData> Run(
    [HttpTrigger(AuthorizationLevel.Function, "post")] HttpRequestData req)
{
    var body = await req.ReadAsStringAsync();
    var eventData = JsonSerializer.Deserialize<IngestEventPayload>(body);
    var blobUrl = eventData?.Data?.BlobUrl;
    var fileName = eventData?.Data?.OriginalFileName ?? "";
    var extension = Path.GetExtension(fileName).ToLowerInvariant();

    var blobClient = new BlobClient(new Uri(blobUrl), new DefaultAzureCredential());
    using var stream = new MemoryStream();
    await blobClient.DownloadToAsync(stream);
    stream.Position = 0;

    var supportedExtensions = new[] { ".csv", ".xlsx", ".xls" };

    if (!supportedExtensions.Contains(extension))
    {
        _logger.LogWarning(
            "Unsupported file type '{Ext}' for file '{FileName}' — moving to quarantine.",
            extension, fileName);
        await MoveToQuarantineAsync(blobClient, fileName);

        // Trả 200 OK để dừng retry — file không hỗ trợ sẽ luôn fail nếu cố parse lại.
        return req.CreateResponse(HttpStatusCode.OK);
    }

    DataTable parsedData = extension == ".csv"
        ? ParseCsv(stream)
        : ParseExcel(stream);

    await WriteToWarehouseAsync(parsedData, fileName);

    _logger.LogInformation("Processed and wrote {RowCount} rows from {FileName} to Warehouse.",
        parsedData.Rows.Count, fileName);

    return req.CreateResponse(HttpStatusCode.OK);
}

private async Task MoveToQuarantineAsync(BlobClient sourceBlob, string fileName)
{
    var quarantineContainer = new BlobContainerClient(
        sourceBlob.GetParentBlobContainerClient().Uri.ToString().Replace("ingest-relay", "ingest-quarantine"),
        new DefaultAzureCredential());
    await quarantineContainer.CreateIfNotExistsAsync();

    var destBlob = quarantineContainer.GetBlobClient(fileName);
    await destBlob.StartCopyFromUriAsync(sourceBlob.Uri);
}
Container quarantine riêng: tạo thêm 1 container ingest-quarantine trong Storage Account nrn-academy-st-dev-{name} (đã tạo ở Phase 2) — giữ tách biệt khỏi ingest-relay để dễ rà soát file bị reject mà không lẫn với file đang chờ xử lý.

2  Parse CSV / Excel thật

// Parse CSV bằng CsvHelper
private DataTable ParseCsv(Stream stream)
{
    using var reader = new StreamReader(stream);
    using var csv = new CsvReader(reader, CultureInfo.InvariantCulture);
    using var dataReader = new CsvDataReader(csv);

    var table = new DataTable();
    table.Load(dataReader);
    return table;
}

// Parse Excel bằng ClosedXML — lấy sheet đầu tiên, dòng 1 là header
private DataTable ParseExcel(Stream stream)
{
    using var workbook = new XLWorkbook(stream);
    var worksheet = workbook.Worksheets.First();
    var range = worksheet.RangeUsed();

    var table = new DataTable();
    bool firstRow = true;

    foreach (var row in range.RowsUsed())
    {
        if (firstRow)
        {
            foreach (var cell in row.Cells())
                table.Columns.Add(cell.GetString());
            firstRow = false;
        }
        else
        {
            var dataRow = table.NewRow();
            int colIndex = 0;
            foreach (var cell in row.Cells())
            {
                dataRow[colIndex++] = cell.GetString();
            }
            table.Rows.Add(dataRow);
        }
    }
    return table;
}
Giả định cấu trúc file: code mẫu trên giả định dòng đầu tiên là header và toàn bộ giá trị đọc dạng string (an toàn nhất khi chưa biết schema cố định). Nếu các file thực tế từ SharePoint có schema cố định (tên cột, kiểu dữ liệu biết trước), nên thêm bước validate schema ngay sau parse — đối chiếu với danh sách cột kỳ vọng, reject hoặc quarantine nếu thiếu cột bắt buộc, tương tự nhánh xử lý file không hỗ trợ ở trên.

// WriteToWarehouseAsync — ghi DataTable vào staging table SIT
private async Task WriteToWarehouseAsync(DataTable data, string sourceFileName)
{
    using var connection = new SqlConnection(_warehouseConnectionString);
    await connection.OpenAsync();

    foreach (DataRow row in data.Rows)
    {
        using var cmd = connection.CreateCommand();
        // Ví dụ ghi vào 1 bảng staging chung — điều chỉnh tên bảng/cột theo schema thật của bạn
        cmd.CommandText = @"
            INSERT INTO dbo.sit_staging_raw (source_file, ingested_at, raw_row_json)
            VALUES (@sourceFile, SYSUTCDATETIME(), @rawRowJson)";
        cmd.Parameters.AddWithValue("@sourceFile", sourceFileName);
        cmd.Parameters.AddWithValue("@rawRowJson", JsonSerializer.Serialize(RowToDict(row)));
        await cmd.ExecuteNonQueryAsync();
    }
}

private static Dictionary<string, object> RowToDict(DataRow row)
{
    var dict = new Dictionary<string, object>();
    foreach (DataColumn col in row.Table.Columns)
        dict[col.ColumnName] = row[col];
    return dict;
}
Vì sao ghi JSON thô vào 1 cột thay vì map đúng từng cột bảng đích: vì schema thật của từng loại file SharePoint (sản phẩm, đơn hàng, báo cáo...) có thể khác nhau, mẫu trên dùng 1 bảng staging chung (sit_staging_raw) lưu nguyên row dạng JSON — pattern này khớp với pattern SIT-STT bạn đã làm ở Velocity Framework Exercise (watermark-based incremental load). Khi đã biết rõ schema cố định cho 1 loại file cụ thể, có thể thêm bảng đích riêng và map cột trực tiếp thay cho JSON.

-- Chạy trong Warehouse wh-vule-sonle-WWI-medallion

// ConsumerStub.cs — Phase 4: query thật từ Lakehouse thay cho placeholder
[Function("ConsumerStub")]
public async Task Run(
    [ServiceBusTrigger("nrn-academy-sbq-query-{name}", Connection = "ServiceBusConnection")]
    string message,
    FunctionContext context)
{
    _logger.LogInformation("Consumer dequeued message: {Message}", message);
    var query = JsonSerializer.Deserialize<QueryRequest>(message);

    // Phase 4: query thật từ Lakehouse Medallion (Gold layer), thay cho placeholder ở Phase 3.
    var resultRows = await QueryLakehouseAsync(query?.RequestId);

    var resultPayload = new
    {
        requestId = query?.RequestId,
        status = "processed",
        rowCount = resultRows.Count,
        data = resultRows
    };

    await _emailSender.SendResultEmailAsync(query?.RecipientEmail, resultPayload);
    await _pushSender.SendResultPushAsync(query?.DeviceTag, resultPayload);

    _logger.LogInformation("Consumer finished processing requestId={RequestId}, rows={RowCount}",
        query?.RequestId, resultRows.Count);
}

private async Task<List<Dictionary<string, object>>> QueryLakehouseAsync(string requestId)
{
    var results = new List<Dictionary<string, object>>();

    using var connection = new SqlConnection(_lakehouseConnectionString);
    await connection.OpenAsync();

    using var cmd = connection.CreateCommand();
    // Ví dụ: query Gold layer table theo điều kiện liên quan tới requestId.
    // Điều chỉnh tên bảng/cột theo schema Gold thật trong lh_vule_sonle_medallion.
    cmd.CommandText = "SELECT TOP 100 * FROM gold.fact_sales WHERE request_ref = @requestId";
    cmd.Parameters.AddWithValue("@requestId", requestId);

    using var reader = await cmd.ExecuteReaderAsync();
    while (await reader.ReadAsync())
    {
        var row = new Dictionary<string, object>();
        for (int i = 0; i < reader.FieldCount; i++)
            row[reader.GetName(i)] = reader.GetValue(i);
        results.Add(row);
    }
    return results;
}
Schema Gold layer thật: tên bảng gold.fact_sales và cột request_ref trong mẫu trên chỉ là ví dụ minh hoạ. Thay bằng tên bảng/view thật trong Medallion Lakehouse của bạn (theo cấu trúc Bronze/Silver/Gold đã xây ở Velocity Framework Exercise) — và điều chỉnh điều kiện WHERE theo cách requestId thực sự map tới dữ liệu cần truy vấn (ví dụ theo khách hàng, theo khoảng thời gian, theo mã đơn hàng...).

💰 Cost Phase 4

Phase 4 không tạo thêm resource Azure mới (Service Principal là Microsoft Entra ID object, không tính phí). Chi phí phát sinh chủ yếu liên quan tới Fabric capacity — việc Warehouse/Lakehouse được query/ghi nhiều hơn sẽ tiêu thụ Capacity Unit (CU) của Fabric.

Vì Warehouse và Lakehouse đã tồn tại từ trước (Velocity Framework Exercise), Phase 4 chủ yếu là công việc tích hợp code/permission, không tạo thêm resource billable mới. Rủi ro cost duy nhất cần theo dõi là nếu khối lượng query/ghi tăng cao bất thường khiến capacity Fabric hiện có không đủ đáp ứng, dẫn tới cân nhắc nâng SKU capacity (F2 → F4...) — nên theo dõi Fabric Capacity Metrics App trong Portal nếu nghi ngờ throttling.

🛡️ Guardrail bổ sung cho Phase 4

  1. Đặt expiry hợp lý cho client secret của Service Principal (6–12 tháng) và ghi lại ngày hết hạn — secret hết hạn sẽ làm toàn bộ Adapter + Consumer mất kết nối Fabric đột ngột, không phải lỗi cost nhưng là rủi ro vận hành cần theo dõi.
  2. Theo dõi Fabric Capacity Metrics App (có sẵn trong mọi tenant Fabric) định kỳ — nếu CU usage thường xuyên chạm 100%, đó là dấu hiệu cần nâng capacity SKU (phát sinh cost thật) trước khi pipeline bị throttle.
  3. Dọn dẹp container ingest-quarantine định kỳ giống ingest-relay — đặt lifecycle policy tương tự đã làm ở Phase 2.
  4. Giới hạn quyền SPN ở mức db_datareader/db_datawriter, không gán db_owner — tránh rủi ro SPN bị lợi dụng để thay đổi schema ngoài ý muốn.
